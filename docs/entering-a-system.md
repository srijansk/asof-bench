# Entering a system

What a system receives, the environment it runs in, the answer rows it writes, and who the entrants are. [PREREGISTRATION.md](../PREREGISTRATION.md) registers every rule this page describes, and is the rule wherever the two seem to differ.

## Entering a system

What a system may see is fixed by sections 8 and 11 of the registration ([section 11](../PREREGISTRATION.md#11-systems-model-and-runs)). In short:

1. From data/v0.1, give a system each item's `question` text and nothing else: not the item's `id`, `family`, `stratum` or any other field, which reveal the answer's shape (an id that begins `F1-change-` says that the status at D differs from the proposal's last offered status at S), and not gold.jsonl, timelines.jsonl, edges.jsonl or REPORT.md, which hold or reveal answers. The harness that runs the system keeps each item's id and writes the answer rows.
2. Run every system in an environment from which no network route leads out except to the answering model's API and, for a system whose store a language model builds, the construction model's API (the construction model, the one that builds a system's store; section 11 names the registered systems of each kind, and [Scoring](scoring.md#scoring) lists them; [section 8](../PREREGISTRATION.md#8-arms-and-the-dated-revision-stream)); the embedding model runs inside that environment (step 4), and no system calls a reranking model. Services that the system runs itself, such as a graph database, a vector index or the embedding model's server, run inside that environment and hold only the system's own software and models and what the system wrote there. From that environment neither data/v0.1, nor any file of this repository other than the system's own adapter and configuration, nor the corpora's live sources (github.com/python/peps, github.com/ethereum/EIPs, github.com/ethereum/ERCs, peps.python.org, eips.ethereum.org and ercs.ethereum.org), their mirrors or a clone of them can be reached, and every provider-side tool (web search, web fetch, code execution with network access, file search and the like) is off. Record that network policy in this form, the routes out and the services inside, and that no provider-side tool is on, in the system's committed configuration. Build the environment first, its software, model weights and database included: the rule holds from the first episode a store ingests or the first item a system answers, whichever comes first, and the committed configuration also says what was installed. A directory beside the checkout is not enough, since an agent there reaches the checkout through `..`, and neither is a separate user account on the same machine, which still reaches the network. An agent's sandbox holds only its inputs. For grep at D:
   1. materialise its inputs, the tree and the log of one arm and date, into a fresh directory ([below](#trees-for-grep-at-d));
   2. copy that directory, and nothing else (no copy of this checkout, data/v0.1, the streams or the clones), into a container or virtual machine, the agent's sandbox, from which no network route leads out;
   3. run the agent outside the sandbox but inside the environment of this step, from which only the answering model's API is reachable (for example through an egress proxy that allows only that host) and neither this checkout nor data/v0.1 is, with the question text and no provider-side tool, so that only its read-only shell commands run inside the sandbox, and write its answer row from outside that environment (section 8).
3. On the corpora, a system receives only what section 11 gives it:
   - closed-book: nothing besides the question;
   - grep at D: an agent with read-only shell tools over its arm's tree as of the end of the item's date (`as_of`) and the log of the commits up to that date beside it, `git-log.txt`, both from `asofbench materialize` (below), and nothing else from the repositories; it is the version-control baseline, a reader of the repository and its history as they stood on the date (the files at D and the log, without diffs or earlier versions);
   - long context: the question plus every episode of the proposal the question names, those recorded after D included, in stream order, for F1, F2 and CF only; the harness takes them from the item's arm's stream, by the item's `proposal` field, which it keeps as it keeps the id;
   - the oracle, reported as a ceiling only: for every proposal of the item's corpus, the statements in effect at the end of the item's date, read from the headers as recorded, in H- as in H+, and in arm CF as the counterfactual stream edits them; it ingests no stream;
   - every other system: its arm's whole stream, the stream file only, never the files beside it, with the episodes recorded after D included (Graphiti's subject to the M0 rule, under which `graphiti-reduced` ingests only part of it); the harness never removes episodes by date. A system may use the question's date through its own interface, for example a temporal filter in its query API, when its committed configuration does so for every item; the registered retrieval systems (BM25, dense and hybrid) do not.
4. Ask each item in each arm its `arms` field lists and the system is entered in, three times (runs 1, 2 and 3). claude-haiku-5-5 answers for every system and builds every LLM-built graph. Send every answering call `thinking: {"type": "adaptive"}` and `output_config: {"effort": "medium"}` and no temperature, with either model: adaptive thinking at effort medium and the default temperature ([section 11](../PREREGISTRATION.md#11-systems-model-and-runs)). Medium is claude-haiku-5-5's default effort, and claude-sonnet-5-5, whose default is high, must be sent it explicitly. Every system that embeds text uses the one embedding model that section 11 names, voyage-4-nano (`voyageai/voyage-4-nano` on Hugging Face, at revision 5fb34e870f49f19e79c94d5e118f5ee730133279), run inside the system's environment behind an OpenAI-compatible embedding endpoint, at its default 2048 dimensions, with its model card's `query` prompt for a question and its `document` prompt for every text the system stores. No system reranks with a cross-encoder or any other reranking model: Graphiti searches with a reciprocal-rank-fusion recipe, and HippoRAG 2's recognition memory, which filters the triples it retrieves for a question with a language model, is part of its method and runs with the construction model, claude-haiku-5-5, in every run, the sensitivity check included (section 11). The harness reads the item's `answer_type` (`status`, `set` or `count`) to write the answer in its shape, a string, a list or an integer; the system receives only the question text, which says what to return.
5. Record each answer's input and output tokens, wall time and tool calls, and write the answer rows below.

### Trees for grep at D

```bash
uv run asofbench materialize --stream streams/h-minus.jsonl --as-of 2021-09-03 --arm H- --data data/v0.1 \
    --out ../asofbench-trees/h-minus-2021-09-03
```

This writes the proposal files as they stood at the end of 2021-09-03 (UTC), rebuilt from the arm's episodes and nothing else, so the tree holds no header its arm withholds and no index such as PEP 0. Each present proposal is written as `<repo>/<series>-<number>`, with the episode's repository, that repository's series in lower case and a PEP's number in four digits, such as `peps/pep-0008`, `EIPs/eip-1559` or `ERCs/erc-20`; an ERC is `EIPs/eip-<number>` until the episode that renames it into the ERC repository.

Beside the files it writes `git-log.txt`, the log of the commits up to the date, taken from the same stream ([section 8](../PREREGISTRATION.md#8-arms-and-the-dated-revision-stream)): one entry per commit that gives the stream an episode recorded by the end of the date, newest first, with the commit id, its recorded time (the episodes' `recorded_at`, in UTC), the path of each proposal file it touched, under the name the tree gives the file, or gave it before a delete (a rename into the ERC repository is listed under its new name, `ERCs/erc-<number>`, only, and a rename within a repository keeps the file's name), and its message exactly as the arm's stream keeps it, each line after four spaces. It holds no diff and no text. For this example the command prints `946 files as of the end of 2021-09-03 (UTC), and git-log.txt with the 9633 commits up to it`, and the 2.1 MB log holds entries such as this one, a commit that changed only withheld header lines (PEP 643's Status and Resolution), so that its H- episode has an empty diff:

```text
commit b8b8a034c5407161d7c977344538c1f7501b7b08
Date: 2020-12-01T15:19:48Z
File: peps/pep-0643

    PEP 643: Mark as accepted (#1724)

```

As this entry shows, a message can name a status even in H-: grep at D reads the messages recorded by the end of D, and a system that reads the stream reads every message, those recorded after D included. With `--arm` and `--data`, a stream that is not the registered one is refused. Grep at D needs one tree per distinct date in each arm, 868 in all, so build each when it is needed, copy it into the agent's sandbox (step 2 above), and delete it after use.

## Answer rows

The harness writes one JSON object per line for each item, arm and run, and the registration requires all nine fields on every row ([section 12](../PREREGISTRATION.md#12-answers-and-scoring)). For example (the answer is only an example of the shape, not the gold):

```json
{"id": "F1-change-PEP-643-2021-09-03", "system": "bm25", "arm": "H-", "run": 1, "answer": "Draft", "tokens_in": 1200, "tokens_out": 4, "wall_s": 2.1, "tool_calls": 0}
```

- `id` is the item's id; `system` is one of the entrants' identifiers, `closed-book`, `bm25`, `dense`, `hybrid`, `grep-at-d`, `long-context`, `hipporag2`, `graphiti`, `graphiti-reduced`, `ppr` (the author's own Personalized PageRank retriever) and `oracle` (see [Entrants and outside entries](#entrants-and-outside-entries)), or a name that an entries file declares (`--entries`, a JSON file of what each system is entered in; see [Scoring](scoring.md#scoring)); `arm` is `H+`, `H-` (or `H−`) or `CF`; and `run` is 1, 2 or 3, written as an integer or a string. Surrounding whitespace is ignored in `arm` and in a string `run`, so " 1 " is run 1, but not in `id`, where it makes an id that is not an item, or in `system`, where it makes an unknown system.
- `answer` is a string for F1 and CF, a list of proposal numbers for F2, F3 and F4, and an integer for F5; any other shape scores zero. A list item is an integer or a string of digits, optionally after PEP, EIP or ERC (`"PEP-8"` reads as 8), and any other item makes the whole answer invalid. Strings are normalised before matching (section 12).
- `tokens_in`, `tokens_out`, `wall_s` and `tool_calls` are the answer's input and output tokens, its wall time in seconds and its number of tool calls (or true or false for whether any tool was called). A row that lacks one of these four, or holds something other than a number there, is still scored: the Accounting table of results.md counts such rows per system, and each cost figure leaves them out, so a token total that no row carries shows "-", not 0.

The scoring run stops (exit 2), scoring nothing, when a line is not a JSON object; a row lacks `id`, `system`, `arm`, `run` or `answer`; an id is not a non-empty string, or a system is not a string or is blank; an arm is not one of the three; a run is neither an integer nor a string (such as 1.0, true or null); or a system is neither one of the eleven nor declared in an entries file. It names up to 50 of the malformed lines, those of the first five kinds, and counts the rest; when no line is malformed, it names every unknown system with the first line that uses it. It lists and sets aside a run labelled other than 1, 2 and 3, an id that is not an item, an answer in an arm the item is not asked in, and an answer outside a system's entries or the run's items. Of several answers to one item from one system in one arm and run, the first stands, reading the answer files in order of their names and each file line by line. Every score counts three runs, and a missing run is wrong.

## Entrants and outside entries

The v0.1 entrants are those of section 11: closed-book, BM25, dense retrieval, hybrid retrieval (BM25 and dense, fused by reciprocal rank), grep at D, long context, HippoRAG 2 ([arXiv:2502.14802](https://arxiv.org/abs/2502.14802)), Graphiti ([arXiv:2501.13956](https://arxiv.org/abs/2501.13956)), self-hosted with telemetry off (entered as `graphiti-reduced` instead if M0's projection exceeds the budget), a Personalized PageRank retriever in the HippoRAG pattern (`ppr`), and the oracle statement store, which is reported as a ceiling only, because a store built from the headers that define the gold wins by construction. Their adapters and configurations are committed to this repository before any scored run, and their maintainers are invited to review them: if you maintain one of these systems, open an issue (see [Reporting problems](../CONTRIBUTING.md#reporting-problems)). A scored run is any run of a system that answers a v0.1 item, and no configuration answers any v0.1 item before the commit that fixes it, so an adapter and its configuration are developed without asking their system any v0.1 question; every run that answered a v0.1 item before that commit is listed in [DEVIATIONS.md](../DEVIATIONS.md), those of the author's `ppr` included ([section 11](../PREREGISTRATION.md#11-systems-model-and-runs)). A system's adapter and configuration are fixed for v0.1 at the commit before its first scored run (for the six pilot systems, the pilot run): any later change to them is listed in DEVIATIONS.md with its date, what changed and the runs it affects, and the results it affects are reported both as registered and as amended; and the published results name, for every run, the commit of each configuration that answered in it. The `ppr` retriever is the author's own (see [Competing interests](../README.md#competing-interests)), and every table of results.md labels it `ppr (author's own)`. Hosted Zep is not entered, because its [terms of service](https://www.getzep.com/legal/terms/) bar benchmarking it for public or third-party disclosure without Zep's prior written consent; Graphiti, the engine at its core, is entered self-hosted instead. crewlore is not entered either (see [Competing interests](../README.md#competing-interests)). LightRAG and a full GraphRAG re-index are deferred to a later version.

Any other system is an outside entry: it is not a v0.1 entrant, and its results are not part of the registered comparison. The scorer scores it once an entries file declares it, such as `{"my-system": {}}` for every arm and family, and every table of results.md shows it as `my-system (outside entry)`, while results.json keeps the id; it is never compared in the headline. To compare it with the registered systems, give it the same inputs under the same rules (see [Entering a system](#entering-a-system)), the same answering model and settings, the same embedding model if it embeds text, and three runs per item, and say wherever you report it that it is an outside entry, with the commit of the configuration that produced it.
