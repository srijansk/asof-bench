# Systems

This directory holds what runs the systems that v0.1 enters ([section 11](../PREREGISTRATION.md#11-systems-model-and-runs)): each registered system's adapter and committed configuration, in a directory of its own; the code the adapters share, in `common/`; the run environment they all run in, in `env/`; the answering harness, `harness.py`, and the reader image in which the single-call entrants and grep at D's agent answer, in `reader/`; grep at D's agent, its sandbox and its runner of the dates, in `grep-at-d/`; and the tests of all of them, in `tests/`. A system's committed configuration records its network policy (the routes out and the services inside, and that no provider-side tool is on) and what was installed.

## The environment rule

Every system runs in an environment from which no network route leads out except to the answering model's API and, for a system whose store a language model builds, the construction model's API, with the embedding model and every other service the system runs itself, such as a graph database, inside it ([section 8](../PREREGISTRATION.md#8-arms-and-the-dated-revision-stream)). From that environment neither data/v0.1, nor any file of this repository other than the system's own adapter and configuration, nor the corpora's live sources, their mirrors or a clone of them can be reached, and no provider-side tool is on. The environment is built first, its software, model weights and database included, and the rule holds from the first episode a store ingests or the first item a system answers, whichever comes first ([Entering a system](../docs/entering-a-system.md)).

## The run environment

A system runs under Docker on two networks: `inner`, an internal network with no route out, which holds the system's container and the services it runs itself, and `outer`, which only the egress proxy joins. The proxy is the one route out.

- `env/egress/` is the egress proxy, `proxy.py`, which uses only the standard library and listens on port 3128. It opens a tunnel only for `CONNECT host:port` to an entry of its allowlist, `EGRESS_ALLOW` (comma-separated `host:port` entries that name hosts by DNS name, by default `api.anthropic.com:443`), comparing the host in lower case and the port exactly. It refuses an IP address, even one that an allowed name resolves to, and any other host or port with 403, any other method, an absolute-form `GET http://...` among them, with 405, a malformed request with 400 and a request head over 16 KiB with 431, and it closes a tunnel that neither side has used for its idle timeout, `EGRESS_IDLE_TIMEOUT`, by default 660 seconds: a minute longer than the 600 seconds that the systems' shared Anthropic client (`common/asofbench_systems/llm.py`) gives a request, since a request made without streaming receives nothing until its response begins, and a tunnel closed sooner would cut a request that the provider may complete and bill, which the client would then send again. It logs one JSON line per request on stdout, with the keys `ts`, `client`, `method`, `target`, `allowed` and `reason`, and nothing of what passes through a tunnel. Its stated limits: it relays TLS uninspected, so it checks the host and port of the `CONNECT` request and never the server name (SNI) that the client's TLS handshake sends inside the tunnel, which is therefore not checked against the `CONNECT` host; and it has no cap on concurrent connections.
- `env/embedder/` is the embedding server, `server.py`, which serves voyage-4-nano (`voyageai/voyage-4-nano` at revision 5fb34e870f49f19e79c94d5e118f5ee730133279) on the CPU in bfloat16, the dtype its weights are published in, at its default 2048 dimensions, on port 8080, and returns each vector in float32, which holds the bfloat16 values exactly. `POST /v1/embeddings` is OpenAI-compatible and answers two model names: `voyage-4-nano-query` embeds with the model's `query` prompt, for a question, and `voyage-4-nano-document` with its `document` prompt, for every text a system stores, in `float` or `base64` (little-endian float32) encoding; `GET /v1/models` lists the two, and `GET /health` names the model, the revision and the dtypes served. The image's build installs `requirements.txt`, which pins every package with its hashes (torch's CPU-only wheel from the PyTorch CPU index, every other package from PyPI), downloads the model at its revision with `fetch_model.py`, which fails the build unless the weights have the registered size and SHA-256, and then, with no network at all, loads the model, checks that its weights are bfloat16, and checks the vectors it gives one text under each prompt. The server loads the model offline when it starts, and refuses to start unless its weights are bfloat16.
- `env/netcheck.py` is the network check, which a system's container runs before it ingests or answers anything, and which uses only the standard library. Through the proxy, each `--allow` target must open, complete a TLS handshake with its certificate verified and answer `GET /v1/models`, sent with no key, with 401, and each `--deny` target must be refused with 403; each `--direct` target, connected to without the proxy, must be out of reach; each `--services` target must accept a connection; and /proc/mounts may show mounts only at the `--mounts` paths and beneath them, besides the container's own root, the three files under /etc that Docker manages and the kernel's own filesystems at and beneath /proc, /sys and /dev. No `--allow` or `--deny` host may resolve from inside the container, since the proxy resolves the hosts it reaches and a name that resolves there is a DNS route out, while each `--services` name must resolve, through Docker's embedded DNS. The gateway check fails on any default route, IPv4 or IPv6, and, when there is none, tries every TCP port from 1 to 65535 on each gateway candidate (the next hop of each IPv4 route through a gateway, the first host address of each IPv4 subnet the container is on, which Docker gives a network's gateway, Docker Desktop's host addresses 192.168.65.1 and 192.168.65.254, the default bridge's gateway 172.17.0.1 and each `--gateway` address), sparing only the container's own addresses and those of the proxy and the services, and fails on any port that accepts a connection. It writes every check and its result to the `--report` file and exits 0 only when every check passes.

## Building and checking the environment

Build the two images, each with its own directory as the context:

```bash
docker build -t asofbench/egress systems/env/egress
docker build -t asofbench/embedder systems/env/embedder
```

The embedder's build downloads the packages and about 0.7 GB of model weights, and ends with the self-test. An image built with `systems/` as its context, such as a system's, has its Dockerfile copy only the files it needs, and `systems/.dockerignore` keeps the tests and caches out of that context. To check the environment by hand, start the two services on throwaway networks, wait until `docker logs asofbench-embedder` shows that the embedder is serving, and run the check from a container on `inner`, here one made from the proxy's image, which has Python. `inner` is created with no address of the host's on it (`com.docker.network.bridge.inhibit_ipv4`), since an internal network leads nowhere out but still gives the host its gateway address, where whatever the host serves on all its addresses answers: on Docker Desktop 29.6.1 the gateway check finds the RPC portmapper and `rpc.statd` of its virtual machine there.

```bash
docker network create --internal -o com.docker.network.bridge.inhibit_ipv4=true asofbench-inner
docker network create asofbench-outer
docker run -d --name asofbench-egress --network asofbench-outer asofbench/egress
docker network connect --alias egress asofbench-inner asofbench-egress
docker run -d --name asofbench-embedder --network asofbench-inner --network-alias embedder asofbench/embedder
docker create --name asofbench-netcheck --network asofbench-inner asofbench/egress python /tmp/netcheck.py \
    --proxy http://egress:3128 --allow api.anthropic.com:443 \
    --deny github.com:443,huggingface.co:443,pypi.org:443,peps.python.org:443,eips.ethereum.org:443,ercs.ethereum.org:443 \
    --deny host.docker.internal:443,gateway.docker.internal:443 \
    --direct 140.82.112.3:443,1.1.1.1:443 --services embedder:8080 --report /tmp/netcheck.json
docker cp systems/env/netcheck.py asofbench-netcheck:/tmp/netcheck.py
docker start -a asofbench-netcheck
```

It prints one line per check and its result. A system's own container runs the same check, with `--services` naming every service the system runs and `--mounts` its input, output and secret paths. Then remove the throwaway containers and networks:

```bash
docker rm -f asofbench-netcheck asofbench-egress asofbench-embedder
docker network rm asofbench-inner asofbench-outer
```

The tests need neither Docker nor the model: they run the proxy in-process against a local echo server, the embedding server's request handling with a fake model, and the network check against stand-in servers, on the repository's own environment, as CI does:

```bash
uv run --frozen --extra dev pytest systems/tests
```

`env/embedder/requirements.txt` is compiled from `requirements.in` by the command its header records, run in `env/embedder/` with uv 0.7.2.

## Answering: the harness and the reader

A system receives each item's question text and nothing else, and the harness that runs it keeps the rest ([section 8](../PREREGISTRATION.md#8-arms-and-the-dated-revision-stream)). `harness.py`, on the host, writes a run's requests, each under a random key, and keeps each key's item, arm, run and answer type to itself; a system's container answers each request; and `harness.py` turns the answers into the answer rows of [section 12](../PREREGISTRATION.md#12-answers-and-scoring), which `asofbench score` scores. The single-call entrants (closed book, and long context and the oracle, whose requests add a context) answer in the reader image, `reader/`, whose runner, `answer_requests`, makes one call per request with the registered settings of `common/asofbench_systems/answer.py`: `max_tokens` 32000, adaptive thinking, effort medium and the answer's JSON schema, with no temperature, top_p or top_k, no prefill and no tool. Each entrant's prompts, settings and network policy are in its directory's `config.json`: [closed-book/config.json](closed-book/config.json), [long-context/config.json](long-context/config.json) and [oracle/config.json](oracle/config.json). Before a system's configuration is fixed, run it on the toy world ([examples/toy_world.py](../examples/toy_world.py)), never on data/v0.1 ([section 11](../PREREGISTRATION.md#11-systems-model-and-runs)).

A run directory, which `harness.py requests` makes outside the repository, holds `input/requests.jsonl`, the requests and nothing else; `output/`, where the container writes; and, beside them, `keys.jsonl` and `plan.json`, which hold each request's item and never leave the host. Mount `input/` and `output/`, never the run directory itself: the reader refuses a requests file that is not alone in its directory. Build the reader's image with `docker build`, not `docker compose build`, which would also rebuild the egress image, whose ID every run records. The key file's path and the images' IDs reach the run as in Graphiti's ([graphiti/README.md](graphiti/README.md#running-an-ingestion)); the reader refuses to start without the IDs. A pilot run of closed book, from the requests to the rows:

```bash
RUN="$PWD/../asofbench-runs/closed-book-pilot"
uv run python systems/harness.py requests --system closed-book --data data/v0.1 --out-dir "$RUN" \
    --items data/v0.1/pilot.json
docker build -t asofbench/reader -f systems/reader/Dockerfile systems
image_id() { docker image inspect --format '{{.Id}}' "$1"; }
export ASOFBENCH_RUN_INPUT="$RUN/input" ASOFBENCH_RUN_OUTPUT="$RUN/output"
export ASOFBENCH_ANTHROPIC_KEY_FILE="$HOME/.config/asofbench/anthropic_api_key"
export ASOFBENCH_IMAGE_IDS="reader=$(image_id asofbench/reader),egress=$(image_id asofbench/egress)"
docker compose -f systems/reader/compose.yaml -p asofbench-reader-pilot run --rm reader \
    answer_requests --requests /input/requests.jsonl --out /output/responses.jsonl --model claude-haiku-5-5
docker compose -f systems/reader/compose.yaml -p asofbench-reader-pilot logs --no-log-prefix egress > "$RUN/output/egress.log"
docker compose -f systems/reader/compose.yaml -p asofbench-reader-pilot down
uv run python systems/harness.py rows --system closed-book --run-dir "$RUN" --out "$RUN/answers.jsonl"
```

Long context and the oracle differ from closed book in two arguments of `harness.py requests`: `--system long-context` or `--system oracle`, and `--streams-dir`, the directory that holds the arms' streams under the generator's names (`h-plus.jsonl`, `h-minus.jsonl` and `cf.jsonl`, which `asofbench build --streams` writes). The harness checks a stream's SHA-256 against the one that the build's `MANIFEST.json` registers for the arm before it reads the stream, hashes the bytes again as it parses them and refuses a stream whose bytes differ (one that changes after the check, or is not whole when it is read), records the name and SHA-256 of each stream it read in `plan.json`, and builds every context before it makes the run directory, so that a stream it refuses leaves nothing behind. A long-context request's `context` is the context description, a blank line and then every episode that the item's arm's stream holds of the proposal the question names, those recorded after the item's date included, in stream order, each as `render_episode` renders it and joined by a line `---`; nothing is cut, so a request over the model's window fails at the API as that request's own `api_error` and its row has a null answer. An oracle request's `context` is the context description, a blank line and then one line for every proposal of the item's corpus that has a file at the end of the item's date, in ascending number, `{proposal}: status {status}; requires {list or -}; replaces {list or -}; superseded-by {list or -}`, read from the file's header as recorded, in the H+ stream for an H+ or H- item and in the CF stream for a CF item, with each distinct stream, corpus and date computed once; the oracle ingests no stream, and is reported as a ceiling and never compared. Every entrant's requests are written in ascending key order, a random permutation of the items' order, so that the requests of one item are not next to one another and the reader's stop after five `api_error` responses in a row (below) fires for a cause that every request shares and not for one item whose context is too long.

`answer_requests` first runs the network check, with the flags every system gives it, no services and the mounts `/input`, `/output` and `/run/secrets`, and answers nothing unless every check passes. It then answers the requests eight at a time, in the file's order, writing one response per request to `output/responses.jsonl` and every model call to `output/usage.jsonl` under the request's key, and records each invocation in `output/run.json`. Its exit status is 0 when every request has a response with an answer; 1 when every request has a response and some of them hold an error code instead of an answer (`refusal`, `max_tokens`, `unparseable`, or `api_error` for an API error that is the request's own, such as a prompt longer than the context window); 2 when it is refused before it starts, the network check fails, or an infrastructure error stops it (after the SDK's retries, the API unreachable, rate-limited, overloaded or failing, or refusing the key), and then the request under way has no response; 3 when five `api_error` responses in a row stop it; and 4 when it crashes, which run.json records with the exception's class. After a status of 2, run the same command with `--resume`: it checks that the requests file and the model are those the run began with, and answers every request that has no response, so that an outage never gives a request a null answer. A status of 3 is different: each of those `api_error` responses is its request's own and stays, but five in a row point at a cause that every request shares, such as a setting that the API rejects, and a resume answers only the requests that have no response. Such a run is discarded and run again in a new run directory once the cause is fixed, never resumed under changed settings. An invocation killed outright leaves `run.lock` in `output/`, and every later invocation exits at once with status 2, naming the lock's holder and the age of its heartbeat: check that no invocation runs (`docker compose -f systems/reader/compose.yaml -p <run> ps -a --status running` must list no `<run>-reader-run-<id>` container), then remove `run.lock` and resume.

`harness.py rows` writes one row per request with the nine fields of section 12, the answer shaped by the item's answer type and in no other way, and a null answer for a request that the system could not answer. A key with no response at all, which a run that stopped and was not resumed leaves, gets a row with a null answer and null costs, and `rows` exits 1: after a stop with status 2 resume the run first, and after one with status 3 discard it and run it again in a fresh run directory, as above, never resuming it. The rows carry the name that `--system` gives, the system's own or, for a toy run, an outside entry's that an entries file declares to `asofbench score` ([examples/README.md](../examples/README.md)).

The tests run without Docker and without the model. `test_harness.py` runs the harness on the toy world and scores its rows, and checks what holds for every entrant's requests, their order, plan.json and the streams each run read, and grep at D's requests, one file for each arm and date with dates.json, and its rows gathered from every date; `test_context_builders.py` checks the long-context and oracle contexts and the harness's reading of the streams, on the toy world and on synthetic streams; `test_answer_requests.py` runs the reader's runner with a stand-in for the call; `test_reader_wiring.py` checks the image, the self-test's reading of a lock, the compose file, the lock and the three single-call entrants' configurations against the code; and `test_answer.py` checks the answering call field by field, and the image's self-test, with the SDK that the reader's lock pins, which the repository's environment does not install, so CI runs it, with the shared client's tests and grep at D's agent loop, as `uv run --frozen --extra dev --with anthropic==0.78.0 --with httpx==0.28.1 python -m pytest systems/tests/test_answer.py systems/tests/test_llm_client.py systems/tests/test_grep_agent.py`. Grep at D's tests are below. Inside the image, with no network, all of them run as `docker run --rm --network none -v "$PWD/systems:/checkout/systems:ro" asofbench/reader python -m pytest -p no:cacheprovider /checkout/systems/tests`, where those that need git or the asofbench package skip; the tree is mounted below `/checkout` and not at the root, since the configuration tests check that no configuration names the directory that holds `systems/`, which is `/` if it is mounted at the root. `reader/requirements.txt` is compiled from `requirements.in` by the command its header records, run in `reader/` with uv 0.7.2.

## Grep at D

Grep at D is the version-control baseline ([section 11](../PREREGISTRATION.md#11-systems-model-and-runs)): an agent that answers each item's question by reading its arm's tree as of the end of the item's date and the log beside it, the files at D and `git-log.txt` that `asofbench materialize` writes, without diffs or earlier versions, with read-only shell commands. Its agent, [grep-at-d/agent.py](grep-at-d/agent.py), answers in the reader image through the reader's runner, as its answering function (the image's command `grep_at_d`), so that the runner's concurrency, resume, usage log, lock and stops hold for it as for the single-call entrants; its commands run in the sandbox, [grep-at-d/sandbox](grep-at-d/sandbox), an image of its own whose command server runs each command under bash in the tree; and [grep-at-d/run_dates.py](grep-at-d/run_dates.py), on the host, builds each date's tree, runs that date's requests and deletes the tree. Its prompts, its tool, its limits, the sandbox and its network policy are in [grep-at-d/config.json](grep-at-d/config.json).

Its environment, [grep-at-d/compose.yaml](grep-at-d/compose.yaml), is the reader's with the sandbox added: the egress proxy and the agent's container on `inner`, the proxy alone also on `outer`, and the sandbox on `sandbox_net` alone, a second internal network with no address of the host on it, which only the agent's container shares. The sandbox holds the date's tree read-only at `/repo` and nothing else of the host: a read-only root, a 16 MiB tmpfs at `/tmp`, which is the commands' `HOME` and `TMPDIR` and is emptied before each command, no capability, no secret and no environment from the host, and at most 256 processes and 512 MiB. Its command server answers `POST /run` with a JSON body `{"command": ...}` and refuses every other request; it runs the command as `bash -c` in `/repo` in a process group of its own, kills the whole group when bash ends or at 20 seconds, and keeps 20,000 characters of stdout and of stderr each, an output cut there ending with a final line `[cut: N characters omitted]`. It runs one command at a time, so that the requests of a date, whose agents share the sandbox, never see one another's processes or scratch files. The agent's network check names the sandbox as the environment's one service, and a sandbox that cannot be reached, or does not answer as the command server does, stops the run with exit status 2, so that no request is given a null answer for it. The sandbox image is `debian:stable-slim` pinned by digest, with gawk and python3, for the command server, installed from the snapshot of the Debian archive taken when that image was built; its build ends with the command server's self-test, with no network.

Every turn of an answer is an answering call with the registered settings and the one tool, `run`, with `tool_choice` auto. The transcript is append-only: each reply goes back as the API sent it, thinking blocks included, followed by a tool result for each of its calls, which is the command's output, then its stderr after a line `stderr:`, then its exit code; each request marks its last block for the prompt cache, since every turn sends the transcript again. After the 40th command's result the user turn ends with the cap's turn, and a tool call after it ends the answer with a null answer and the error `command_cap`, the request's own outcome; `tool_calls` in the row is the number of commands run. The agent's own build-time self-test, `grep_at_d --self-test`, makes one answer of two turns through the installed SDK to a stand-in for the API and checks each request.

`harness.py requests --system grep-at-d` writes grep at D's requests one file for each arm and date, `input/<file>/requests.jsonl`, `<file>` the arm's stream's name and the date (such as `h-minus-2021-09-03`), each alone in its directory with an empty `output/<file>/` beside it, and `dates.json`, which maps each file to its arm and date and holds nothing of the items; `plan.json` records each file's SHA-256 and dates.json's, and dates.json is written last. `run_dates.py` checks the run directory and the build against plan.json, then for each date in dates.json's order builds the tree with `asofbench materialize --arm --data` from the arm's registered stream into a fresh directory under `--trees-dir`, which must be outside the repository, runs the agent with that date's `input/<file>/`, `output/<file>/` and tree, saves the proxy's log as `output/<file>/egress.log`, takes the environment down and deletes the tree, whatever the run did. A pilot run, from the requests to the rows:

```bash
RUN="$PWD/../asofbench-runs/grep-at-d-pilot"
TREES="$PWD/../asofbench-trees"
mkdir -p "$TREES"
uv run python systems/harness.py requests --system grep-at-d --data data/v0.1 --out-dir "$RUN" \
    --items data/v0.1/pilot.json
docker build -t asofbench/sandbox systems/grep-at-d/sandbox
docker build -t asofbench/reader -f systems/reader/Dockerfile systems
image_id() { docker image inspect --format '{{.Id}}' "$1"; }
export ASOFBENCH_ANTHROPIC_KEY_FILE="$HOME/.config/asofbench/anthropic_api_key"
export ASOFBENCH_IMAGE_IDS="reader=$(image_id asofbench/reader),egress=$(image_id asofbench/egress),sandbox=$(image_id asofbench/sandbox)"
uv run python systems/grep-at-d/run_dates.py --run-dir "$RUN" --data data/v0.1 --streams-dir streams \
    --trees-dir "$TREES" --model claude-haiku-5-5
uv run python systems/harness.py rows --system grep-at-d --run-dir "$RUN" --out "$RUN/answers.jsonl"
```

`run_dates.py` exits 0 when every date is done with every request answered, 1 when some requests hold an error code, 2 when it is refused before it starts, a tree cannot be built, a date's run stops with exit status 2 or is killed, or the environment does not start the run, 3 when a date's run stops after five `api_error` responses in a row, and 4 when a date's run crashes. After a 2 or a 4, run the same command again: it skips the dates that are done, resumes the one that stopped with `--resume` and goes on. After a 3, discard the run directory and write the requests again in a new one once the cause is fixed, never resuming it, as for the reader's runs. A date's run that is killed outright leaves `run.lock` in its `output/<file>/`, removed as the reader's is. A killed `run_dates.py` can leave its last tree under `--trees-dir`, a directory named after the date's file: remove it before the next run.

To check the sandbox by hand, with the two images built as above, run it alone on the toy world's tree and send it commands. `exec` runs a command as the sandbox's user in its container, and a throwaway container of the reader image on the project's `sandbox_net` sends one through the command server, as the agent does; the key file is a made-up one, since nothing here calls the API:

```bash
CHECK="$PWD/../asofbench-sandbox-check"
uv run python examples/toy_world.py "$CHECK/toy"
mkdir -p "$CHECK/input" "$CHECK/output" && printf 'sk-ant-not-a-key\n' > "$CHECK/key"
export ASOFBENCH_RUN_TREE="$CHECK/toy/tree" ASOFBENCH_RUN_INPUT="$CHECK/input" \
    ASOFBENCH_RUN_OUTPUT="$CHECK/output" ASOFBENCH_ANTHROPIC_KEY_FILE="$CHECK/key"
grep_check() { docker compose -f systems/grep-at-d/compose.yaml -p asofbench-grep-check "$@"; }
grep_check up -d sandbox
grep_check exec -T sandbox bash -c 'id; touch /repo/x; touch /x; ls -A /repo; cat /etc/passwd; cat /proc/mounts'
grep_check exec -T sandbox python3 -c 'import socket; socket.create_connection(("1.1.1.1", 443), timeout=5)'
grep_check exec -T sandbox bash -c 'getent hosts api.anthropic.com github.com; echo "getent: $?"'
run_in_sandbox() { docker run --rm --network asofbench-grep-check_sandbox_net asofbench/reader python -c \
    'import asyncio, sys; from grep_at_d.agent import Sandbox, render; print(render(asyncio.run(Sandbox().run(sys.argv[1]))))' "$1"; }
run_in_sandbox 'yes > /dev/null'
run_in_sandbox "head -c 5000000 /dev/zero | tr '\0' a" | tail -c 120
grep_check down
```

Each `touch` must fail, as must the connection and the lookup; `id` must show uid 10001, `/etc/passwd` is the image's own, and `/proc/mounts` must show, besides the kernel's filesystems, the read-only root and the three files under `/etc` that Docker manages, only the tree at `/repo`, read-only, and the tmpfs at `/tmp`; the `yes` loop comes back after 20 seconds, killed, and the 5,000,000 characters come back as 20,000 and the line `[cut: 4980000 characters omitted]`.

Grep at D's tests run without Docker and without the model: `test_command_server.py` runs the command server on a temporary tree (its commands, exit codes, both outputs, the cut and its final line, the timeout and the killing of the process group, the scratch directory emptied, one command at a time, and the refusal of every other request); `test_grep_agent.py` runs the agent loop through the pinned SDK against a stand-in for the API (the settings and the tool on every turn, the append-only transcript and its thinking blocks, the cache markers, the counts, the cap and its user turn, the final answer and every way a request is not answered), and through the reader's runner and the real command server, and its stdlib tests check the registered strings, the sandbox client and the network check; `test_run_dates.py` runs `run_dates.py` on the toy world with a stand-in for `docker compose`, checking that each date's tree is built for it, used for its requests alone and deleted, and how it resumes and stops; and `test_grep_wiring.py` checks the compose file, the sandbox's Dockerfile and config.json against the code.
